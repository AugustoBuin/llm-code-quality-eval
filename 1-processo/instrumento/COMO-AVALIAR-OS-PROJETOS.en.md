# How to evaluate the 5 projects and fill in the ground truth

Complete guide to producing the **human ground truth** — the true reference score
for each project, against which the AI's error is measured: `erro_abs = |nota_IA − nota_humana|`.

> **Note on anonymization.** In this public repository the evaluated projects appear only as
> **P1–P5**. The real names and paths live solely on your machine, in the file `projetos.local.config`
> (in the `3-codigos/coleta/` folder), which is deliberately kept out of version control. Wherever this guide
> says "the folder of project Pn", read it as "the real subfolder mapped to Pn in your `projetos.local.config`".

**Order of work:**
1. Read the rubric (`rubrica-qualidade-codigo.en.md`) and lock in your score anchors.
2. Evaluate the 5 projects **blind** (category by category) — see the 🔒 rule in section 4.
3. Fill in `gabarito.csv` (instructions in `gabarito_INSTRUCOES.en.md`).
4. Run `node gabarito_check.js` to validate and sum.

---

## 1. Scope rule — evaluate exactly what the AI saw

The AI ran at the **root of each repository**, with read/search permission, and the instruction
"explore the files in the current directory". In other words, it saw **all of the project's source code
(frontend + backend together)**, minus dependencies. So you give **one holistic score per
category, for the entire project** — do not split front and back into separate scores.

**✅ In scope (score it):** all source code — `.ts .tsx .js .jsx .css .sql .prisma`,
configs (`package.json`, `tsconfig`, `docker-compose`, lint) and whatever defines the architecture.

**❌ Out of scope (ignore — it does not count and only gets in the way):**
- `node_modules/`, `.git/`, `dist/`, `build/`, `package-lock.json`
- **generated code** (e.g. `generated/prisma/` folders, generated by Prisma — it is not the team's work)
- binaries/assets: `.png .pdf .svg .jpeg`
- `docs/` — documentation, not code (it can give context, but it is not what the rubric measures)
- AI context files (`.clinerules`, `CLAUDE.md`, `GEMINI.md`) — these were **hidden from the AI**
  during collection, so you ignore them too, to keep parity

The project folders live inside the directory you pointed to in `projetos.local.config`
(the `ABP` variable).

## 2. Map of each project — where to look

They are all full-stack TypeScript (React on the front + Node/Express + Prisma/Postgres on the back),
split into a backend folder and a frontend folder. (The real folder names live in your
`projetos.local.config`.)

> **Public version:** the per-project map (folder names, number of files and scope notes) is
> withheld because it would make the teams identifiable. It lives in `projetos.local.config`.

*In all of them, start with: the `src/` folder of each
side (back and front), the `package.json` (scripts and dependencies), the Prisma schema and the SQL migrations.*

## 3. Rubric checklist — so you do not forget anything

5 categories, **each from 0 to 20** (full detail in `rubrica-qualidade-codigo.en.md`).
For **each project**, walk through the 5 criteria looking at these places:

- **c1 — Functioning** (ISO 25010 Functional Suitability): does the code run and deliver what is expected?
  Look at entry points (`server`/`index`/`app`), routes/controllers, front↔API integration,
  and dead code / `TODO` / mocks left behind.
- **c2 — Readability** (Clean Code): names, formatting, consistency. Look at components and services,
  whether there is a lint standard configured **and followed**, useful comments vs. noise.
- **c3 — Structure** (DRY / SRP): short, cohesive functions, no duplication, single responsibility.
  Look at the size of the files, repeated logic, separation of layers.
- **c4 — SOLID**: abstractions, dependency injection, coupling. Look at services/repositories,
  use of interfaces, and whether the business rule depends directly on the ORM.
- **c5 — Non-functional**: security, **tests**, performance. Look at auth/secrets handling,
  check *for yourself* whether there are real tests (and whether they are worth anything) and what the `test` script in
  `package.json` actually does.

> ⚠️ **File count ≠ quality.** A project may have dozens of trivial test files,
> or zero tests because there genuinely are none. Do not trust aggregate numbers: open and judge the content.

---

## 4. Two rules that protect the validity of the experiment

1. **Score the whole project** (frontend + backend) → one value 0–20 per category, 5 per project.

2. **🔒 Score BEFORE looking at the AI's answers.** Do not open `dados.csv` or `problemas.csv`
   until you have closed the ground truth. If you read the problems the AI pointed out first, your score
   anchors to it and the `erro_abs` drops artificially — this would **invalidate the entire thesis** (the
   ground truth must be independent of the AI). Score **blind**, then compare. **This is the most
   important point of all.**

---

## 5. How to make sure you do not get the arithmetic wrong

- You **only type integers from 0 to 20**; `gabarito_check.js` computes the sum `G(p) = c1+c2+c3+c4+c5`
  and validates everything. **Zero manual arithmetic = zero calculation error.**
- **Calibrate first:** read the rubric and lock in your anchors (what a 20 is, a 15, a 10, a 5, a 0).
  Use the same yardstick across all 5 projects.
- **Consistency:** score **one category across all 5 projects at once** (all the c1s, then all
  the c2s…) instead of closing one project at a time — it reduces the "halo effect" and drift between projects.
- Write **1 line of justification per project** in the `observacoes` column — it helps a lot in
  the oral presentation.

---

## TL;DR — the flow in one sentence

Read the rubric → score the 5 projects **blind**, category by category, looking at the source code
(front + back, ignoring deps/generated/assets) → fill in `gabarito.csv` → run
`node gabarito_check.js`. Done: out comes `gabarito_computed.csv` with the reference score of each project.
